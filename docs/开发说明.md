# 开发说明

这份给人看，说明本地怎么用容器开发、线上怎么部署。Cursor 改代码时读的是仓库根目录的 `AGENTS.md`。那份文件必须留在根目录，Cursor 才会每次自动加载。

Innobuddy 只通过 Docker 运行。本地和线上用同一套镜像，配置文件和 Compose 覆盖文件不同。不要用 `npm run dev`、`npm run dev:no-auth`、`npm start` 或 PM2 启动。

可提交的是 `config/secrets/` 里的两份密封配置，其中的秘钥只保存腾讯云 SSM 引用。`.env.docker.local` 和 `.env.docker.online` 由启动脚本生成或写回，不要提交。

## 没有预发环境

目前没有预发、测试或 staging 环境。线上 Ubuntu 虚拟机就是生产环境，对外提供服务。

切忌把未在本地容器里验证过的改动直接部署到线上。下面这些都算直接动线上：

- 在线上仓库 `git pull` 之后执行 `./scripts/docker-up-online.sh`
- 手改线上 `.env.docker.online` 后重启容器
- 在线上容器里试迁移、清库、换密钥或换镜像

`./scripts/docker-up-online.sh` 会立刻重新构建镜像，并重启正在运行的容器。本地验证通过之前，不要执行它。

## 两套环境

| | 本地 | 线上（生产） |
|------|------|----------------|
| 配置 | `.env.docker.local` | `.env.docker.online` |
| 启动 | Windows：`.\scripts\docker-up-local.ps1`；Ubuntu：`./scripts/docker-up-local.sh` | `./scripts/docker-up-online.sh` |
| Compose | `docker-compose.yml` + `docker-compose.local.yml` | `docker-compose.yml` + `docker-compose.online.yml` |
| 访问 | http://127.0.0.1:3000 | `http://<虚拟机IP>:3000` |
| 端口 | 只绑定 `127.0.0.1` | 发布到虚拟机网卡 |

镜像是 Ubuntu Server 24.04 LTS amd64。`PUBLISH_PORT` 默认 `3000`。容器内工作区是 `/research`，对应宿主机的 `HOST_WORKSPACE_PATH`。本地默认挂仓库里的 `./workspace`，线上默认 `/data/innobuddy/research`。

## 工作台的控制面和数据面

工作台把「屏幕上现在是哪一块」和「这一块里面的内容」分开。改界面时先判断改动落在哪一边。

控制面只回答屏幕状态。实现在 `src/lib/shell/surface.ts`。工作区页面 `/workspace/:id` 的查询参数就是这份状态，由 `parseShellSurface` 读入、`buildWorkspaceHref` 写回。壳组件切换视图时只改这条地址，不另起一套路由，也不把屏幕状态写进 `localStorage`。

| 参数 | 含义 |
|------|------|
| `view` | `agent`、`skills`、`library`、`research`、`settings`。缺省是 `agent`，地址里不写 |
| `research` | 当前 Deep Research 会话。只在 `view=research` 且不是新建入口时出现 |
| `intake=1` | 打开 Deep Research 的新建入口。此时不带 `research` |
| `file` | 右侧预览的文件路径。只在 `view=agent` 时生效 |

数据面是这些状态指到的现成数据，仍走原来的接口和存储。壳层负责把结果画出来，检索、鉴权、路径校验和会话内容留在 `src/lib/` 与 `src/app/api/`。

| 屏幕上的东西 | 数据从哪里来 |
|--------------|----------------|
| 项目 | 已有工作区，`/api/workspaces` |
| 左侧 Agent 会话 | 该工作区已有的 Agent 会话，存在浏览器 `localStorage` |
| 左侧 Deep Research | 已有研究会话，`/api/deep-research/sessions` |
| 对话消息 | 当前 Agent 会话自己的消息 |
| 技能库 | `/api/skills` |
| 文献检索结果 | `POST /api/paper-study/search` |
| 预览文件 | `file` 指向的工作区文件，内容走原来的文件接口 |

新增一种屏幕状态时，补到 `ShellSurface` 和上表，并让地址能来回解析。新增一种内容时，接已有接口；没有现成接口，再在 `src/lib/` 和对应的 `src/app/api/**/route.ts` 里加。不要为工作台再造一张任务表。

## 本地容器化开发

在仓库根目录执行。

Windows：

```powershell
.\scripts\docker-up-local.ps1
```

Ubuntu：

```bash
chmod +x scripts/docker-up-local.sh
./scripts/docker-up-local.sh
```

已有 `config/secrets/docker.local.env` 时，脚本用腾讯云凭据管理把 `AUTH_SECRET` 和 `DEEPSEEK_API_KEY` 写进 `.env.docker.local`。解密凭据来自环境变量 `TENCENTCLOUD_SECRET_ID`、`TENCENTCLOUD_SECRET_KEY`，否则读取桌面上的 `SecretKey.csv`。不要把这组 API 密钥写进仓库。

没有密封配置、也没有 `.env.docker.local` 时，脚本会生成一份。把 `DEEPSEEK_API_KEY` 改成可用密钥后，再执行一次启动脚本。浏览器打开 http://127.0.0.1:3000。

改的是宿主机上的源码。容器里跑的是镜像构建结果，没有热更新。改完代码后重新执行上面的启动脚本，脚本会 `--build` 并重启本地容器。

宿主机上的 `npm` 只用来检查，不负责把应用跑起来：

```bash
npm install
npx tsc --noEmit
npm run lint
npm test
npm run build
```

改了 `src/lib/db/schema.ts` 之后，在宿主机生成迁移并提交 `drizzle/` 下的新文件。迁移在容器启动时执行。

只在本人这台机器、且没有其他人能访问时，才可以把 `.env.docker.local` 里的 `AUTH_MODE` 设为 `disabled`。这样每个请求都是管理员。线上不要用这个值。

本地至少确认这三件事，再考虑线上：

1. http://127.0.0.1:3000 能打开
2. 登录或注册后能进入工作区。首页是工作空间列表；进入空间后，技能库、文献库、Deep Research 和设置都在工作台里。镜像内带有仓库 `skills/`，打开技能库时会把这些原生技能同步进数据库
3. 需要对话时，模型请求能返回

停止和日志：

```powershell
docker compose --env-file .env.docker.local -f docker-compose.yml -f docker-compose.local.yml logs -f innobuddy
docker compose --env-file .env.docker.local -f docker-compose.yml -f docker-compose.local.yml down
```

## 线上部署

再强调一次：线上就是生产，没有可以先试一次的预发环境。只部署已经在本地容器里验证过的版本。

在 Ubuntu 虚拟机上安装 Docker Engine 24+ 和 Compose v2，把仓库放到虚拟机后执行：

```bash
chmod +x scripts/docker-up-online.sh
./scripts/docker-up-online.sh
```

已有 `config/secrets/docker.online.env` 时，脚本从 SSM 凭据 `innobuddy-docker-online` 取回秘钥并写入 `.env.docker.online`。虚拟机上需要能调用 SSM 的腾讯云 API 密钥。没有这份密封配置时，第一次运行会生成 `.env.docker.online`。至少填写：

- `DEEPSEEK_API_KEY`
- `HOST_WORKSPACE_PATH`：虚拟机上真实存在的目录
- `WORKSPACE_ROOTS=/research`
- `AUTH_SECRET`：一长串随机值
- `AUTH_MODE=local`
- `AUTH_COOKIE_SECURE=false`：当前站点是明文 HTTP。前面加上 HTTPS 之后再改为 `true`，然后重新执行启动脚本

`AUTH_SINGLE_ADMIN=true` 时，公开注册不能再创建管理员。第一次登录前引导唯一管理员：

```bash
umask 077
openssl rand -base64 32 > /tmp/innobuddy-admin-password
docker compose --env-file .env.docker.online -f docker-compose.yml -f docker-compose.online.yml exec -T innobuddy \
  node /app/admin-cli/scripts/bootstrap-admin.js \
  --email admin@example.com --name Administrator \
  < /tmp/innobuddy-admin-password
```

密码从你自己掌握的渠道发出去，然后删除临时文件。

升级时先在本地验证，再在虚拟机上备份，然后：

```bash
git pull
./scripts/docker-up-online.sh
```

保留上一版镜像，直到登录、一个普通用户的工作区、以及一次模型回复都正常。迁移预检如果发现两条工作区记录会冲突，会停下来；它不会删除或改派工作区。

当前按明文 HTTP 发布在 `PUBLISH_PORT`。需要 HTTPS 时，用 Nginx 或 Caddy 反代到 `127.0.0.1:3000`，并转发 `Upgrade`，否则流式响应会被掐断。证书就绪后把 `AUTH_COOKIE_SECURE` 改为 `true`，再执行一次线上启动脚本。

停止：

```bash
docker compose --env-file .env.docker.online -f docker-compose.yml -f docker-compose.online.yml down
```

日志把上面的 `down` 换成 `logs -f innobuddy`。

## 排错

| 现象 | 处理 |
|------|------|
| `workspace root missing` | `HOST_WORKSPACE_PATH` 必须在宿主机上存在；`WORKSPACE_ROOTS` 是容器内路径，一般是 `/research` |
| `no AI API key detected` | 看 SSM 是否把 `DEEPSEEK_API_KEY` 写进环境文件，然后重新执行对应环境的启动脚本 |
| SSM 取秘钥失败 | `config/secrets/*.env` 指向 `ap-shanghai`，调用方需要 `GetSecretValue` 权限 |
| 容器马上退出 | `docker compose logs innobuddy` |
| 端口被占用 | 改该环境的 `PUBLISH_PORT`。本地只占 `127.0.0.1` |

改代码时的仓库约定见仓库根目录 `AGENTS.md`。


## Isolated macOS development

Start OrbStack or Docker Desktop before running the local profile. The local
Compose override selects linux/amd64 because the Dockerfile installs x64 Node.

For an independent local configuration, create a protected .env.docker.local
file with a unique AUTH_SECRET and COMPOSE_PROJECT_NAME. Set AUTH_MODE=local,
AUTH_COOKIE_SECURE=false, PUBLISH_PORT=3000, HOST_WORKSPACE_PATH=./workspace
and WORKSPACE_ROOTS=/research. Use AUTH_SINGLE_ADMIN=false only for isolated
local testing, where the first registered user becomes administrator.
A blank DEEPSEEK_API_KEY permits authentication testing but cannot run model tasks.

Run the existing script while preserving this local configuration:

    INNOBUDDY_LOCAL_ENV_ONLY=true bash scripts/docker-up-local.sh

This explicit option skips SSM materialization and requires an existing local
environment file. The default SSM-backed startup remains available.

Verify registration, login, logout and account isolation before configuring
OneID. OneID integration still requires the tenant issuer, client ID, protected
client secret and approved callback URL.

### Local HTTPS before the certificate is issued

HTTPS does not depend on the Tencent Cloud order. A throwaway self-signed
certificate is enough to exercise the parts that only exist behind TLS:
`AUTH_COOKIE_SECURE=true`, the `Secure` flag on session and OneID cookies, and an
`https://` OneID callback URL.

    bash scripts/local-tls.sh              # writes deploy/tls-local/ (git-ignored)
    INNOBUDDY_LOCAL_ENV_ONLY=true INNOBUDDY_LOCAL_HTTPS=true bash scripts/docker-up-local.sh

The app is then on `https://localhost:8443` through Nginx. `http://127.0.0.1:3000`
still answers, but do not log in through it while the overlay is active: the app
now sets `Secure` cookies, so a browser on plain HTTP stores nothing and login
loops back to the login page. Use one origin per session.
`deploy/nginx/local.conf` mirrors `deploy/nginx/innoscale.conf` except for the
hostname, so the production switch reuses a path already proven locally.
Validate the config with
`docker compose -f docker-compose.yml -f docker-compose.local.yml -f docker-compose.https.local.yml
exec https nginx -t`.

Behind a proxy, a route handler cannot rebuild the browser-facing origin: Next.js
takes the scheme from `X-Forwarded-Proto` but the host from its own bind address,
so `request.nextUrl.origin` becomes `http://0.0.0.0:3000` even when `Host` and
`X-Forwarded-Host` are set. Middleware is unaffected. Redirects out of route
handlers must therefore use a relative `Location`, or derive the origin from
operator configuration such as `AUTH_OIDC_REDIRECT_URI`.

The certificate is untrusted by default, so the browser shows a warning until it
is added to the system trust store; `Secure` cookies work either way. Never point
`deploy/tls/` at these files and never ship them: they carry no CA signature and
exist only on this machine. Do not commit `deploy/tls-local/`.


## Innoscale 域名与 HTTPS（证书签发后启用）

对外品牌统一为 Innoscale，主域名为 `innoscale.cn`。内部包名、容器名、数据卷和数据库无需改名。HTTPS 不依赖 OneID。已有 OV 订单尚待提交企业资料，不能把订单视为已签发证书。

新增 `docker-compose.https.yml` 为可选覆盖文件，不影响现有 HTTP 启动方式。需要 Docker Compose 2.24.4+（支持 `!override`）。先在本地容器验证，再部署生产；不要在证书未就绪时执行线上切换。

1. 完成 OV 企业审核和域名验证，确认签发的证书覆盖 `innoscale.cn`。如需 `www`，先确认其在证书 SAN 内，再扩展 Nginx 的 `server_name`；当前配置仅发布主域名。
2. 从腾讯云下载 Nginx 格式证书，将完整证书链保存为 `deploy/tls/fullchain.pem`、私钥保存为 `deploy/tls/privkey.pem`。目录权限 700、私钥权限 600。此目录及本地 `SecretKey.csv` 已排除 Git 和 Docker 构建，严禁提交。
3. 确认 DNS 指向生产服务器，安全组放行 TCP 80/443。备份当前 Compose 配置及运行镜像信息，保留回滚版本。不要把备份或渲染后的含密钥 Compose 配置提交到仓库。
4. 使用以下相同 Compose 参数先执行 `run --rm --no-deps https nginx -t`，通过后执行 `up -d --no-build`。覆盖文件会将应用端口限制为本机，并通过容器环境覆盖开启 `AUTH_COOKIE_SECURE=true`，不必改写线上密钥配置。

```bash
docker compose --env-file .env.docker.online \
  -f docker-compose.yml -f docker-compose.online.yml -f docker-compose.https.yml \
  run --rm --no-deps https nginx -t

docker compose --env-file .env.docker.online \
  -f docker-compose.yml -f docker-compose.online.yml -f docker-compose.https.yml \
  up -d --no-build
```

切换会重建应用容器，安排短维护窗口。验证 HTTP 跳转、证书链与域名、登录 Cookie 的 Secure 属性、文件上传和流式对话；确认外网不能直连 3000。此后 `docker-up-online.sh` 会在检测到 `deploy/tls/` 下已有证书链和私钥时自动附加 HTTPS 覆盖文件并打印提示；若日志显示 `starting HTTP-only`，说明证书路径不对或文件为空，此时不要继续上线。撤销 HTTPS 请删除该目录后重启，而不是手改 Compose 参数。

回滚：用相同三个 Compose 文件执行 `stop https`，再仅使用基础和 online 两个文件执行 `up -d --no-build innobuddy`，恢复原 HTTP 配置。回滚后浏览器可能需要清除原 Secure 会话 Cookie 并重新登录。

### OV 续期与替换

OV 订单自动续费当前未开启；付款续费不等于证书自动签发或自动部署。到期前 30 天检查续期报价并确认费用，完成必要的企业与域名复核。将新证书和私钥安全替换到现有文件路径（保持目录挂载），使用上述三个 Compose 文件执行 `exec -T https nginx -t`，通过后执行 `exec -T https nginx -s reload`。保留上一组证书以便回滚。用外部 TLS 检查确认新到期日，建议运维系统每天检测证书剩余有效期，在 30/14/7 天告警。当前仅提供续期操作方案，未创建自动购买或定时任务。

## Optional OneID login (Innoscale)

OneID is disabled by default. Configure the server-only `AUTH_OIDC_*` variables
in the active Docker environment only after obtaining tenant application details.
Keep `AUTH_MODE=local`, set `AUTH_SINGLE_ADMIN=false`, and use secure cookies with
HTTPS. Existing local accounts remain available. See [OneID setup and MySQL
integration](oneid.md) for callback registration, verified email requirements,
local tests, and the separate MySQL migration procedure. Cloud account API keys
must never be used as OneID application credentials.

## Keycloak local identity environment

Run `./scripts/keycloak-local.sh`. This keeps the business database on SQLite and
uses a separate MySQL 8.0 instance exclusively for Keycloak. No business database
migration or cloud credentials are involved. See `docs/keycloak-local.md`.
`AUTH_OIDC_PROVIDER=keycloak` disables public local-password login/registration,
and routes login/registration server-side; a short-lived logout marker preserves
the existing frontend logout flow. Its default is `oidc`,
which preserves existing deployments. HTTPS deployment configuration is unchanged.
